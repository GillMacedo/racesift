# racesift: group and rank Go data race reports from go test -race

[![CI](https://github.com/GillMacedo/racesift/actions/workflows/ci.yml/badge.svg)](https://github.com/GillMacedo/racesift/actions/workflows/ci.yml) [![MIT license](https://img.shields.io/badge/license-MIT-blue)](LICENSE)

**A Claude Code skill and Go CLI for Go developers whose `go test -race` run or CI log is full of `WARNING: DATA RACE` reports. It groups repeated reports into distinct races, ranks them by how many tests hit them, shows both code locations and the tests involved, and adds hints for common causes like an unguarded map or a mixed atomic. It can also compare two runs to show races a branch added.**

The race detector prints a 30-line report for every race it sees, and one missing lock can produce dozens of reports across many tests. `racesift` reads that output and gives each race once: the two lines of your code that conflict, where each goroutine started, and which tests hit it. The skill then has Claude read both locations, name the shared variable, and propose a fix.

## What you can ask Claude

- "CI failed with WARNING: DATA RACE. Here's the log. What's wrong?"
- "Which of these data races should I fix first?"
- "Does my branch add any new data races compared to main?"
- "Why does the race detector say my map is racing?"

## Install

As a Claude Code plugin:

    claude plugin marketplace add GillMacedo/racesift
    claude plugin install racesift@racesift-marketplace

Or as a CLI with Go 1.22 or newer. It has no dependencies:

    go test -race ./... 2>&1 | go run github.com/GillMacedo/racesift/plugin/scripts@latest review

## Usage

    racesift review [--json] [--fail] [FILE ...]
    racesift compare [--json] [--fail] BASE HEAD

- Reads plain `go test -race` output, `-v` output, `go test -json` output, `go run -race` output from a program, and GitHub Actions logs with their timestamps. With no FILE, or with `-`, it reads stdin.
- `--json` prints the full result, including every frame of the first report in each group.
- `--fail` exits 1 when `review` finds races, or when `compare` finds new ones. Without it, both exit 0. Exit code 2 means bad usage or a file it couldn't read.
- `compare` matches races by the pair of functions involved, ignoring line numbers, so an edit elsewhere in a file doesn't make an old race look new. Two races in the same pair of functions count as one there.

## Hints

| ID | Finds |
|---|---|
| RS101 | A map read and written by different goroutines |
| RS102 | An atomic operation on one side and a plain access on the other |
| RS103 | A slice appended to while another goroutine uses it |
| RS104 | A standard library value, such as `bytes.Buffer` or `strings.Builder`, shared between goroutines |
| RS105 | The same line racing with itself, like a shared counter |
| RS106 | A function and a closure it started using the same variable |
| RS107 | Every frame from your code is in `_test.go` files |
| RS108 | One side has no frame from your code |

RS000 means a report was cut off or couldn't be read. Hints come from the stack's shape. Treat them as leads and read the code.

## Limits

- **It can only group what the race detector printed.** The race detector reports races that happen during a run. A clean run doesn't mean the code is race free, and the number of reports can change from run to run.
- **It doesn't name the variable.** Go's reports give addresses, not variable names. The skill has Claude read the code to find it.
- **Lost frames.** Go's reports sometimes drop the caller when the access is inside the runtime or `sync/atomic`. Those sides show a runtime frame and get `RS108`.
- **Test names are a best guess with `t.Parallel`.** Without `-json`, a report is matched to the test that the next "race detected during execution of test" line belongs to.
- **Grouping is by line.** Two races on one variable from different lines are separate races. "Lines in more than one race" helps join them.
- Logs hold file paths and function names from your code. `racesift` reads them locally and never uses the network, but Claude sends what it reads to its model.

## FAQ

**How do I read a Go data race report?** Each report has two accesses: the current one and a "Previous" one, from different goroutines, with no synchronization between them. The first frame from your code on each side is where to look. `racesift` pulls those out for you.

**Why does the race detector report the same race many times?** It reports each conflicting pair of accesses it sees, and the same code runs in many tests. `racesift` groups reports by their two code locations.

**How do I find which data races my PR introduced?** Save `go test -race` output from main and from your branch, then run `racesift compare --fail main.log branch.log` in CI.

**Why does `runtime.mapaccess` show up in my race report?** A map is being read and written by goroutines with no lock. That's RS101.

**Does it work with `go test -json` and gotestsum?** It reads `go test -json` output directly. It hasn't been tested on gotestsum's own output formats.

**Is it an MCP server?** No. It's a skill with one Go source file, so `go run` is all it needs.

## Tested on

- **Real race output from programs in `examples/programs/`:** plain, `-v`, `-json` and `go run -race` output on Go 1.27, plus plain output on Go 1.22. Every hint from RS101 to RS108 fired on real output there. The GitHub Actions log is that real output with timestamps added, since this was built without CI access.
- **Real projects:** logrus at the commit before `fbf9913` and zap at the commit before `7c80d7b`, each with the fix commit's new test, in `examples/logs/real/`. Both point at the code each fix changed.
- **Clean runs stay quiet:** the healthy example package, logrus at `fbf9913`, and logrus at `6ef0748`, its latest commit when tested, each print only "No data race reports found."
- **Integration tests** in `tests/` run `go test -race` on the examples fresh and check the result.

It hasn't been tested in a fresh Claude session, on Windows or macOS, on gotestsum output, or through `go run ...@latest`, which needs the published repo.

Contributions are welcome, from people and from people working with AI agents. See [CONTRIBUTING.md](CONTRIBUTING.md). Good first issues are [listed here](https://github.com/GillMacedo/racesift/issues?q=is%3Aissue+is%3Aopen+label%3A%22good+first+issue%22).

### How pull requests work

1. **Open a PR.** Fork the repo, work on a branch, and keep it to one change. Write a title that says what changes for users, because it becomes the changelog line: `feat:` goes under Added and `fix:` under Fixed.
2. **Automatic check.** Code changes need tests, and `make test` must pass. Changes over 30 lines need a linked open issue (`Closes #<number>`), and a PR can have at most 800 changed lines. If something is missing, a comment tells you what to fix.
3. **Review.** Claude reviews each PR automatically. Code PRs also get a security review and are tested in a sandbox. The review then merges the PR or asks for changes. PRs that change CI, agent settings, dependencies or build files go to the maintainer, as does anything the security review doesn't clear.
4. **Release.** A merge that changes what users install becomes a new version within about 20 minutes, with a GitHub Release and, if the project has one, its npm package. Docs and CI changes wait for the next release.
